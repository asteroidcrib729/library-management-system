# Development Plan 10: Operational Hardening and Recovery

## Document information

- **Status:** Completed
- **Project:** Library Management System
- **Plan:** `development-plan-10.md`
- **Depends on:** `development-plan-01.md` through `development-plan-09.md`
- **Milestone:** Deliver guarded database health, backup, and restoration operations.

## 1. Objectives

- Let administrators inspect SQLite integrity, foreign keys, schema compatibility, and circulation-state consistency.
- Create transactionally consistent backups using SQLite's online backup API.
- Keep backups in an application-managed directory with collision-safe names.
- List backup size, timestamp, schema version, integrity, and compatibility.
- Restore only validated backups created inside the managed backup directory.
- Automatically create a safety backup immediately before every restoration.
- Preserve the live database when validation or restoration fails.

## 2. Safety and authorization policy

- All maintenance operations require an active administrator account.
- Backup filenames are generated by the application and cannot contain caller-supplied paths.
- Restore accepts a filename only and rejects traversal or files outside the managed directory.
- A restore candidate must pass SQLite integrity and foreign-key checks.
- A restore candidate must use exactly the application's current schema version.
- Restoration copies the candidate into a temporary database before atomic replacement.
- A timestamped `pre-restore` safety backup is created before replacement.
- Backup creation and health checks are read-only with respect to operational records.

## 3. Health checks

The health report includes:

- SQLite `integrity_check` result
- foreign-key violation count
- applied and expected schema versions
- database file size
- active-loan/copy-status inconsistency count
- fine/settlement-state inconsistency count
- overall healthy or unhealthy state

This milestone requires no schema migration.

## 4. CLI commands

- `db-health`: inspect the active database (administrator only)
- `backup`: create and validate an online backup (administrator only)
- `backups`: list managed backups and compatibility (administrator only)
- `restore-backup <filename>`: restore after typing an explicit confirmation phrase (administrator only)

## 5. Deliverables

- Backup-directory application setting
- Maintenance service and health, backup, and restore result types
- Integrity, foreign-key, schema, and logical consistency checks
- Online backup and guarded atomic restore implementation
- CLI health, inventory, backup, and restore displays
- Tests for authorization, consistency, snapshots, validation, traversal, and recovery
- Updated README and completion record

## 6. Acceptance criteria

- Healthy initialized databases pass every health check.
- Logical copy/loan and fine/settlement inconsistencies are reported.
- Backups are valid SQLite snapshots independent of later live changes.
- Repeated backups cannot silently overwrite an existing file.
- Backup inventory includes corrupt or incompatible files without opening them for restoration.
- Non-administrators cannot inspect, create, list, or restore backups.
- Path traversal and unmanaged restore sources are rejected.
- Corrupt or schema-incompatible backups cannot replace the live database.
- Successful restoration recovers the selected snapshot and creates a safety backup.
- Pytest, Pyrefly, Ruff lint, Ruff formatting, package, and live CLI smoke checks pass.
